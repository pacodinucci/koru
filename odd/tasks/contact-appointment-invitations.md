## Accepted flow and implementation contract
The user authorized the previously proposed complete flow with S4 after confirming reservations and a 48-hour lifetime. Existing contact follow-up status stays independent. Initial-questionnaire (`admission`) contacts only; ADMIN/SUPERADMIN only, retaining contacts permissions. The header action is `Agendar cita`. Offer 1–3 future, distinct, nonoverlapping intervals with explicit Mexico City timezone, duration, modality/location, optional message and visible recipient. Review summary before `Enviar invitación por mail`. Retain form data on errors.
All proposed intervals reserve the same admission-interview agenda against overlapping invitations and confirmed appointments. Confirming one releases other intervals; rejecting all or administrator cancellation releases all; reservations expire 48 hours from initial successful invitation delivery. Resend does not extend that deadline. Availability must be correct without a cron job. Public, opaque-token link requires no account and shows choices, confirmation, expiry or cancellation. GET never confirms, rejects or otherwise mutates business state. Repeating a successful confirmation is safe and cannot create another appointment. Failed initial sends must not leave a misleading sent invitation or blocking reservation. Notifications go to the family and initiating administrator on confirmation; rejection notifies the initiating administrator. Appointment email failure must not lose a confirmed reservation.
Assumptions: dedicated interview agenda rather than blocking unrelated school calendar events. Calendar display synchronization was optional in the proposal and is not included. Duration defaults to 30 minutes; reuse America/Mexico_City for input/display. No arbitrary recipient override; use persisted contact/initiator addresses. Do not modify existing contact status or permission defaults.

### Shared HTTP contract (both writers follow exactly)
GET `/api/dashboard/contacts/admission/[id]/appointments` -> `{ invitation: AppointmentInvitationView | null }` (latest invitation).
POST same route body `{ durationMinutes: number, mode: "IN_PERSON" | "ONLINE", location: string, message?: string, startsAt: string[] }` -> `{ invitation: AppointmentInvitationView }`. `startsAt` are ISO UTC instants derived from Mexico-local input. At most one active invitation per contact. Refuse replacement while active; expose cancel first.
POST `/api/dashboard/contacts/admission/[id]/appointments/[invitationId]` body `{ action: "resend" | "cancel" }` -> `{ invitation: AppointmentInvitationView }`.
GET `/api/public/appointments/[token]` -> `{ invitation: PublicAppointmentInvitationView }`.
POST same public route body `{ action: "confirm", slotId: string }` or `{ action: "reject" }` -> `{ invitation: PublicAppointmentInvitationView }`.
All errors `{ error: string }`, non-2xx; never leak tokens via administrative response, logs or mail payload persistence. Public responses only expose first name (or generic recipient), schedule/mode/location/message/status, not contact answers/email/admin identifiers. Private/no-store responses; same-origin protection on mutation. Token invalid returns generic 404; expired/cancelled states render safe explanation. Public pages use noindex and no-referrer, no external resources.
Shared type file authored by parent: `src/modules/appointments/appointments.contract.ts`. Backend never edits UI; frontend never edits schema/server/routes/contract.
